# 应用内更新

右上角「⋮ → 检查更新」显示当前页面、服务器和当前设备的版本、稳定版更新内容以及升级进度。
「加粗字体」移至「外观 → 阅读设置」，仍是所有引擎共用的偏好。

窗口按发现新版、更新中、完成后等待页面刷新分别展示。更新说明先显示三条原文摘要，
完整说明与更新记录可展开查看。每次打开窗口自动检查更新，窗口内自动刷新进度；
不再显示手动检查按钮或旧版本备份提示。
安装期间重新登录仍可查看历史，顶部显示「正在更新」。恢复会话和写操作暂缓，
输入草稿保留；设备确认退出维护状态后，只恢复当前查看的会话，不自动补发被拒绝的消息。
一般忙碌、权限失败和无法确认更新结果仍分别提示，不作为正常维护状态隐藏。

此入口更新 cc-remote 的 Web/PWA、Relay 和当前 Wrapper；其他设备单独更新。
Electron 应用本体和 Harmony HAP 仍通过各自安装渠道更新。
首次使用需要先通过既有部署流程安装包含此功能的 Relay/Web/Wrapper。
旧 Relay 或未接入维护通道的设备会显示不可用，不会通过聊天执行更新命令。

## 一次性启用

在设备的独立终端中执行：

```bash
cc-remote ui-updates enable
```

macOS 以原桌面用户运行，使用 LaunchAgent 启动独立升级任务。
Linux 通过安装的管理命令获取管理员授权，安装只允许操作该固定安装目录的专用 helper 和
systemd Unix socket 服务；Wrapper 保持 `NoNewPrivileges=yes`，通过套接字的实际对端 UID
校验调用者，不依赖 Wrapper 内执行 sudo，也不降低服务原有的权限隔离。
当前要求主机有可用的 systemd。源码运行、非托管安装和没有 systemd 的容器不支持设备端按钮升级。
不会在浏览器中索取或存储 sudo 密码。

如果已经使用 `cc-remote update --relay-ssh …` 配置并验证了管理员 SSH 入口，
可以明确允许当前设备同时更新配对服务器：

```bash
cc-remote ui-updates enable --allow-relay-update
```

该选项复用已有 SSH 授权，不授予新的服务器权限。未启用时，服务器需要升级会阻止设备安装；
服务器已是兼容版本则无需该权限。启用不重启 Wrapper，下一次检查更新即可读取配置。
使用自定义 `CC_REMOTE_STATE_DIR` 时，附加 `--control-socket /absolute/state/control/control.sock`，
必须与当前 Wrapper 的私有控制套接字一致。

禁用后不会再接受新的更新，尚未进入安装的任务会安全取消；已经开始的安装继续完成或回滚：

```bash
cc-remote ui-updates disable
```

## 执行与恢复

- 只接受管理员配置的 GitHub 仓库当前最新稳定版本，不接受命令、下载 URL、环境变量或降级请求。
- 设备先校验安装包并完成服务器更新，再检查哪些操作会受 Wrapper 重启影响；下载和服务器更新期间
  不锁定本地会话，设备安装前重新检查期间新增的任务。已由独立 Claude 服务接管的会话和问答、
  有完整恢复记录的共享 Codex daemon 回合，以及已连接的 DSH 原生任务可继续运行，不要求全部会话空闲。
  仍等待 Wrapper 内执行的任务、私有侧聊、排队消息、提交和设置修改、临时附件依赖，以及尚未确认归属的活动；
  Codex/DSH 待回答问题和 Wrapper 调度的 Work 作业仍需完成。等待期间可继续使用会话或取消更新；
  开始安装后暂停新操作，直到重新连接。不会强行中断模型或接管原生 CLI。
- 更新由独立的 launchd/systemd 任务运行。关闭面板、浏览器断线或 Wrapper 重启不会取消已接受的更新。
  页面重开时查询原任务；启动结果未知时保留原编号，重复点击不会创建第二个 OS 任务。
- 原提交没有收到确认时，页面自动按原请求编号读取设备记录，包括已不在最新任务位置的记录。
  查到记录后恢复进度；暂未查到时显示「更新尚未启动」并提供重试，继续沿用原编号，防止延迟到达的
  首次请求与重试重复安装。查询本身不启动任务；读取失败不会当成未启动，提交错误也不会被普通轮询清掉。
  旧设备不支持按编号查询时保留原请求，用户仍可显式重试，不会自动重发安装命令。
- UI 与终端使用同一套安装锁、激活记录、任务归属检查、SHA256 校验、不可变版本目录、
  事务回滚及保留清理。安装锁用于防止两个安装器同时切换目录，不代表所有会话都被锁定。
  只有安装器确认可以切换并进入服务停止、快照、切换和验证阶段后才暂停新操作；
  过期的 UI 进度记录本身不能禁止聊天。
  普通更新不重启独立 Claude 服务。协议或 Claude SDK/服务契约变化仍要求协调维护，不允许按钮绕过。
- 页面刷新仍检查输入草稿、附件、未保存编辑和待确认操作；有未保存内容时提示处理，不自动丢弃。

策略保存在安装根目录 `ui-update-policy.json`，升级记录在 `ui-update-jobs/`。
安装器的实际激活状态在 `activation.json` 和 `activation-jobs/`；终端更新也写入这些记录。
Mac 日志是对应任务的私有 `.log`，Linux 日志可按 `cc-remote-ui-update-<id>` 查询 journal。
公开面板只返回阶段和受控原因，不返回本地路径、进程输出、命令或凭据。
完成的 macOS 任务会卸载其 launchd 注册，Linux 临时单元由 systemd 回收；磁盘上的小型记录保留用于去重。
记录上限为 1024，达到上限后拒绝新更新，由管理员核实维护，不删除旧记录来绕过去重。

「结果待确认」意味着启动确认丢失、工作进程无法确认或安装结果需要检查。
服务器更新提交后 SSH 短暂断线会自动重查原事务，最多三次；仅在服务器的去重记录允许时，
沿用同一编号补交请求。仍无法确认时结束当前设备升级尝试，保留 `upstream-update.json`，
本地设备尚未安装，会话可继续使用。用户重试会先核对同一服务器事务，确认完成后才安装设备；
不会因为网络失败创建第二个服务器更新任务。
设备会自动检查原进程身份、安装锁、激活记录、`current` 和实际服务健康。控制进程退出但安装器
仍在运行时只跟踪原任务；安装器也已退出时，独立恢复任务核实结果或恢复原配置、私有数据快照和
旧版本，然后验证服务健康。已提交成功的安装不会为了补齐 UI 状态而回滚数据。
自动恢复最多三轮；仍有权限、磁盘或服务故障时保留明确原因，并提供「重新核对并恢复」入口。
恢复动作沿用原请求，不重新提交安装。完成或安全回滚后解除维护限制，可以再次发起更新。
不要删除记录、换编号绕过未决事务，也不要将未知结果直接标记为成功。

临时 TLS 连接中断、下载超时、HTTP 408/429/5xx 和 SSH 传输失败有有限次数重试。
证书不可信、SSH 身份验证失败或主机密钥不匹配会分别报告；不会关闭证书校验或不断重试权限错误。

## 通信边界

维护使用独立 schema 1 通道，聊天协议版本不变：

- 浏览器 `/api/updates/{machine_id}` 使用既有登录 Cookie、设备权限及写操作精确 Origin 校验。
- Wrapper `/ws/updates` 使用设备 Bearer 凭据，动态吊销会在请求和响应时重新检查。
- 设备使用现有私有 Unix 控制通道提交安装前的维护预留；任务归属检查与预留之间不挂起。
- 每设备请求数量、帧大小、HTTP 请求体和记录数量有上限。Relay 不保存升级任务状态。

这条通道不提供任意远程管理 shell。升级只能复用设备管理员事先启用的安装和服务器权限。
